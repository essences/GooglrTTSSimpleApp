# コントローラーのクラス化方針（段階的移行）

## 目的
- UI コントローラーをクラス化し、依存矢印・状態オーナーシップ・イベントライフサイクルを明確にする。
- 既存の createXxxController ファクトリ経由の呼び出し互換を維持しつつ段階的に移行する。

## ガイドライン
- **状態の単一ソース**: `appState` を状態のオーナーとし、クラス内では参照/更新のみ。重複保持は禁止。
- **依存の注入方向**: `app.js` (オーケストレーター) → Controller → Service の一方向に限定。UI からサービスを直接 import しない。
- **イベントライフサイクル**: `init()` で addEventListener、`destroy()` で removeEventListener を行う構造を目標とする（現状はオーケストレーターからの登録を維持し互換ファクトリで段階移行）。
- **ハンドラ束縛**: クラスフィールド（アロー関数）で `this` を固定し、リスナー登録時の文脈逸脱を防ぐ。
- **サービス境界**: TTS/ストレージ/履歴計算など副作用を持つ層は薄いインターフェースオブジェクトでコントローラーに渡し、モック容易性を確保。
- **スモーク確認**: 移行ステップごとに「生成→試聴→履歴再生→ダウンロード」のスモークを記録する。

## 現状ステップ（2025-12-06）
- Generation/Script/Speaker 各コントローラーをクラス化し、createXxxController ファクトリは互換のまま new を返す形に変更済み。
- 各コントローラーに `init/destroy` を追加し、自身で UI イベントを登録・解除する形へ移行。`app.js` はライフサイクル呼び出しのみ。

## 次ステップ案
1. TTS/ストレージ/履歴のサービス依存をインターフェース経由に整理し、直接 import を削減する（UI層は依存注入に統一）。
2. `destroy()` を実際に呼び出す経路（画面リロード、モーダル破棄等）は必要に応じて設計し、リスナー解除の確認チェックリストを作成する。
3. 移行ごとにスモークテスト結果をこのドキュメント末尾へ追記する（日時/担当/結果）。

## 依存方向チェック（2025-12-06）
- appエントリ (`src/js/app.js`): コントローラーとサービス/UIをimportし、上位のみ。下位からの逆参照なし。
- コントローラー層: 他コントローラーやappエントリへのimportなし。Generation/Script/Speakerはサービス・UIのみ参照。
- サービス層: コントローラー・appエントリをimportせず、下方向のみ（例: `gemini-service` は api-client と constants のみ）。
- 循環参照は検出されず、依存矢印は app→controller→service/UI の一方向。

## スモークテスト記録（2025-12-06 手動）
- シナリオ: APIキー設定 → サンプル原稿入力 → 生成ボタン → 進捗完了 → プレビュー再生 → ダウンロード → 履歴から再生/ダウンロード。
- 結果: すべて成功（ブラウザ手動）。回帰なし。
- 備考: destroy 経路は未使用（リロード時にブラウザが破棄）。今後 destroy 呼び出しが必要な場合はチェックリスト追加。
