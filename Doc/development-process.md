# 開発プロセス・ルール

## プロジェクト情報
- **プロジェクト名**: 研修ナレーションスタジオ（シンプル版）
- **作成日**: 2025-11-24
- **開発手法**: アジャイル開発（スクラム + TDD/BDD要素）
- **重点方針**: **常に動作する状態を維持し、E2Eテストで確認しながら開発を進める**

---

## 1. 開発の基本原則

### 1.1 コアプリンシプル

#### ✅ Working Software First（動くソフトウェア優先）
- **常に動作する状態を維持する**ことを最優先とする
- 機能は小さく分割し、1つずつ動作確認しながら実装する
- 壊れた状態を長時間放置しない

#### ✅ Outside-In Development（外側から内側へ）
- **UIから実装を開始**し、ユーザーの操作フローに沿って開発する
- 画面に表示され、操作できる状態を早期に作る
- バックエンドロジックは後から詰めていく

#### ✅ Continuous Integration（継続的統合）
- 各機能実装後、すぐに統合して動作確認する
- モックやスタブは最小限にし、実際のAPI接続を早期に行う
- 統合問題を先送りにしない

#### ✅ User-Centric Testing（ユーザー中心のテスト）
- **実際にブラウザで操作して動作確認**することをテストの基本とする
- 自動化より手動E2Eを優先（シンプルなアプリのため）
- ユーザーが実際に使う手順でテストする

## 2. Definition of Done (DoD)

### 2.1 PBIレベルのDoD（必須）

各PBI（プロダクトバックログ項目）が完了したと判断する基準：

- [ ] **受入基準がすべて満たされている**
  - PBIに記載された受入基準チェックリストがすべて✅になっている

- [ ] **E2Eテストが成功している**
  - **ブラウザ上で実際にユーザー操作を行い、期待通りに動作することを確認済み**
  - テストシナリオが実行され、すべてのステップが成功している
  - スクリーンショットまたは動作確認記録が残されている

- [ ] **既存機能が壊れていない（リグレッションテスト）**
  - 新機能追加により既存機能が影響を受けていないことを確認済み
  - 主要な操作フロー（APIキー設定→原稿入力→音声生成）が正常動作する

- [ ] **エラーハンドリングが実装されている**
  - 想定されるエラーケースで適切なエラーメッセージが表示される
  - アプリがクラッシュしない

- [ ] **コードが可読性・保守性を満たしている**
  - 変数名・関数名が意図を表している
  - 複雑なロジックにコメントが記載されている
  - マジックナンバーがない（定数化されている）

- [ ] **主要ブラウザで動作確認済み**
  - Chrome で動作確認済み
  - Firefox または Edge で動作確認済み（少なくとも1つ）

- [ ] **セキュリティチェック完了**
  - ユーザー入力がサニタイズされている
  - XSS脆弱性がない
  - APIキーなどの機密情報が適切に扱われている

### 2.2 スプリントレベルのDoD

スプリント全体が完了したと判断する基準：

- [ ] すべてのPBIがPBIレベルのDoDを満たしている
- [ ] **スプリントゴールが達成されている**
- [ ] **統合E2Eテストが成功している**（エンドツーエンドの操作フロー確認）
- [ ] スプリントレビューでデモが成功している
- [ ] 技術的負債が記録されている
- [ ] 次スプリントへの引き継ぎ事項が整理されている

## 3. 開発ワークフロー

### 3.1 PBI実装の標準フロー（Outside-In TDD）

各PBIを実装する際の推奨手順：

#### Phase 1: UI First（UIから着手）
```
1. HTMLマークアップ作成
   - モックアップを参考にUIを実装
   - ダミーデータで表示確認
   - ブラウザで見た目を確認

2. CSS スタイリング
   - デザインを適用
   - レスポンシブ対応（必要な場合）
   - ブラウザで表示確認

3. イベントハンドラー仮実装
   - ボタンクリック等のイベントリスナーを追加
   - console.log で動作確認
   - ブラウザで操作確認
```

**確認ポイント**: ✅ 画面が表示され、ボタンが押せる状態になっている

---

#### Phase 2: Integration（統合・実動作）
```
4. APIクライアント実装または既存API利用
   - 必要なAPI呼び出しを実装
   - エラーハンドリング追加
   - console.log でレスポンス確認

5. データバインディング
   - APIレスポンスをUIに反映
   - ローディング状態の実装
   - ブラウザで実際のデータ表示確認

6. ステート管理実装
   - 状態管理コードを追加
   - localStorage連携（必要な場合）
   - ブラウザで状態が正しく保存・復元されることを確認
```

**確認ポイント**: ✅ 実際のAPIと接続し、データが取得・表示される

---

#### Phase 3: Refinement（改善・エラー処理）
```
7. エラーハンドリング強化
   - ネットワークエラー対応
   - APIエラーレスポンス対応
   - バリデーション追加
   - エラー通知UI表示

8. エッジケース対応
   - 空データ、異常値のハンドリング
   - ブラウザで意図的にエラーを発生させて確認

9. リファクタリング
   - コードの可読性向上
   - 重複コード削除
   - 定数の抽出
```

**確認ポイント**: ✅ 異常系も適切にハンドリングされる

---

#### Phase 4: Testing & Documentation（テスト・ドキュメント）
```
10. E2Eテスト実施
    - テストシナリオに従って手動操作
    - すべてのステップで期待通りの動作を確認
    - スクリーンショット取得（オプション）

11. リグレッションテスト実施
    - 既存機能が壊れていないことを確認
    - 主要フローを再度実行

12. テスト結果記録
    - テストケース実施記録を残す
    - 発見したバグを記録・修正

13. コードレビュー（オプション）
    - セルフレビューまたはペアレビュー
    - チェックリストで確認

14. ドキュメント更新
    - 必要に応じて技術メモ更新
    - README更新
```

**確認ポイント**: ✅ DoDをすべて満たし、リリース可能な状態

---

### 3.2 実装サイクル（イテレーション）

**推奨サイクル**: 半日〜1日で1つの機能を完成させる

```
午前: Phase 1 (UI First)
  - HTMLマークアップ
  - スタイリング
  - イベントハンドラー仮実装
  → ブラウザで動作確認

午後: Phase 2-3 (Integration & Refinement)
  - API統合
  - データバインディング
  - エラーハンドリング
  → ブラウザでE2Eテスト

翌日: Phase 4 (Testing & Documentation)
  - 詳細なE2Eテスト
  - リグレッションテスト
  - ドキュメント更新
  → PBI完了
```

**重要**: 1日の終わりには必ず動作する状態にする

## 4. テスト戦略

### 4.1 テストピラミッド（本プロジェクト版）

本プロジェクトはシンプルなブラウザアプリのため、**E2E手動テスト中心**とする。

```
        ▲
       / \
      /   \     ← E2Eテスト（手動）: 70%（メイン）
     /     \
    /       \   ← 統合テスト（手動）: 20%
   /         \
  /___________\ ← 単体テスト（手動/軽微）: 10%
```

### 4.2 E2Eテストの実施方法

#### 基本原則
- **実際にブラウザで操作してテストする**
- テストシナリオに従って手順を実行する
- 各ステップで期待結果を確認する
- 問題があればその場で修正する

#### テストシナリオの構造

```markdown
## テストケース: [機能名]

### 前提条件
- [ ] ブラウザを開いている
- [ ] アプリケーションが起動している
- [ ] （その他の前提条件）

### テスト手順
| # | 操作 | 期待結果 | 結果 |
|---|------|----------|------|
| 1 | [操作内容] | [期待される結果] | ✅/❌ |
| 2 | [操作内容] | [期待される結果] | ✅/❌ |
| ... | ... | ... | ... |

### 事後条件
- [ ] （確認すべき状態）

### テスト結果
- **実施日時**: 2025-11-24 14:30
- **テスター**: [名前]
- **ブラウザ**: Chrome 120.0
- **判定**: ✅ Pass / ❌ Fail
- **備考**: （発見した問題、改善点など）
```

### 4.3 テストケーステンプレート格納場所

```
/Doc/test-cases/
  ├── sprint1/
  │   ├── TC001_api_key_management.md
  │   ├── TC002_script_editor.md
  │   └── ...
  ├── sprint2/
  │   └── ...
  └── regression/
      └── main_flow.md（リグレッションテスト用）
```

## 5. テストケース一覧

### 5.1 Sprint 1 テストケース

#### TC001: APIキー管理機能
**目的**: APIキーの設定・保存・検証・削除が正しく動作することを確認

**テスト手順**:
1. アプリを開く → APIキー入力モーダルが表示される
2. 無効なAPIキーを入力して保存 → エラーメッセージが表示される
3. 有効なAPIキーを入力して保存 → 検証が成功し、モーダルが閉じる
4. ページをリロード → APIキーが保持されている
5. 設定画面から削除ボタンをクリック → 確認ダイアログが表示される
6. 削除を実行 → APIキーが削除され、再度入力モーダルが表示される

#### TC002: 原稿入力エディタ
**目的**: 原稿入力と文字数カウントが正しく動作することを確認

**テスト手順**:
1. 原稿入力エリアに「Hello World」と入力 → 文字数カウントが「11」と表示される
2. テキストを追加入力 → 文字数がリアルタイムで更新される
3. テキストをすべて削除 → 文字数カウントが「0」と表示される
4. プレースホルダーテキストが表示される

#### TC003: スピーカー設定
**目的**: 2名の話者設定が正しく動作することを確認

**テスト手順**:
1. Speaker A の名前タグに「Joe」と入力 → 入力が反映される
2. Speaker A の音声プリセットで「Kore」を選択 → 選択が反映される
3. Speaker A のスタイルメモに「calm, professional」と入力 → 入力が反映される
4. Speaker B も同様に設定 → すべて正しく入力される
5. 設定内容が状態として保持される

---

### 5.2 Sprint 2 テストケース

#### TC010: 音声生成メインフロー（エンドツーエンド）
**目的**: 原稿入力から音声生成、再生、ダウンロードまでの一連のフローが動作することを確認

**テスト手順**:
1. APIキーを設定
2. 原稿に以下を入力:
   ```
   Joe: Welcome to our training session.
   Jane: Thank you Joe, I'm excited to learn!
   ```
3. Speaker A に「Joe」、音声「Kore」を設定
4. Speaker B に「Jane」、音声「Puck」を設定
5. 「音声を生成」ボタンをクリック
6. 進捗バーが表示され、生成が進む
7. 生成完了後、セクションプレビューに音声プレーヤーが表示される
8. 再生ボタンをクリック → 音声が再生される
9. ダウンロードボタンをクリック → WAVファイルがダウンロードされる

**期待される状態**:
- すべてのステップが成功する
- エラーが発生しない
- 音声ファイルが正しく再生される

---

### 5.3 リグレッションテストケース（全スプリント共通）

#### RG001: メインフロー（煙テスト / Smoke Test）
**目的**: アプリの基本的な動作が壊れていないことを確認

**実施タイミング**: すべてのPBI実装後、毎日の終わり

**テスト手順**:

**所要時間**: 約5分

**判定**: すべてのステップが成功すればPass

## 6. ブランチ戦略（Git利用時）

### 6.1 ブランチモデル: GitHub Flow簡易版

```
main (常に動作する状態)
  ├── feature/PBI-001-project-setup
  ├── feature/PBI-002-api-key-management
  ├── feature/PBI-003-api-client
  └── ...
```

### 6.2 ブランチ運用ルール

#### mainブランチ
- **常に動作する状態を維持**（絶対ルール）
- DoDを満たした機能のみマージ
- 壊れたコードは絶対にコミットしない

#### featureブランチ
- PBI単位でブランチを作成
- ブランチ名: `feature/PBI-XXX-short-description`
- 作業中はこまめにコミット（動かなくてもOK）
- 完成したらmainにマージ

#### コミットメッセージ
```
[PBI-XXX] 簡潔なタイトル

- 詳細な変更内容
- 実装したこと
- 確認したこと

Test: ブラウザで動作確認済み
```

---

### 6.3 コミットタイミングとルール

#### コミットの原則
- **こまめにコミット**: 小さな単位で頻繁にコミットする
- **動作する状態でコミット**: mainブランチは常に動作する状態を維持
- **featureブランチは柔軟に**: 作業途中でもコミット可能
- **意味のある単位**: 1つのコミットは1つの意図を持つ

---

#### コミットすべきタイミング

##### 1. Phase完了時（推奨）
実装フローの各Phase完了後にコミット

```
Phase 1完了 → コミット
  ↓
Phase 2完了 → コミット
  ↓
Phase 3完了 → コミット
  ↓
Phase 4完了 → コミット
```

**例**:
```bash
# Phase 1: UI First 完了
git add src/index.html src/styles.css
git commit -m "[PBI-002] APIキー入力モーダルUIを実装

- モーダルHTML構造作成
- スタイリング適用
- 基本レイアウト確認

Test: ブラウザで表示確認済み"

# Phase 2: Integration 完了
git add src/app.js src/api-client.js
git commit -m "[PBI-002] APIキー保存・検証機能を実装

- localStorage保存処理実装
- API検証機能実装
- エラーハンドリング追加

Test: ブラウザで保存・検証動作確認済み"
```

---

##### 2. 機能単位の完了時（必須）
PBIまたはサブタスクが完了し、DoDを満たした時

**条件**:
- [ ] 受入基準を満たしている
- [ ] E2Eテスト成功
- [ ] 既存機能が壊れていない
- [ ] コードが動作する

**例**:
```bash
git add .
git commit -m "[PBI-002] APIキー管理機能を完全実装

- APIキー入力・保存・検証・削除機能実装
- XSS対策実施
- エラーハンドリング完了

Test: TC001実施済み（Pass）"
```

---

##### 3. 毎日の終わり（推奨）
1日の作業終了時、作業内容を保存

**条件**:
- featureブランチで作業中
- 翌日の作業再開をスムーズにするため

**例**:
```bash
git add .
git commit -m "[PBI-002] WIP: APIキー検証処理を実装中

- API呼び出し処理を実装
- エラーハンドリングは未完了

Note: 作業途中、明日続行"
```

**WIPコミットのルール**:
- コミットメッセージに `WIP:` を付ける
- mainにマージしない
- 翌日作業再開時、必要に応じてsquash

---

##### 4. 長時間作業の区切り（推奨）
2-3時間の作業の区切り

**理由**:
- 作業ロストの防止
- ロールバックポイントの確保
- 進捗の可視化

**例**:
```bash
# 午前中の作業
git commit -m "[PBI-002] APIキー入力UIの実装完了"

# 午後の作業
git commit -m "[PBI-002] APIキー検証ロジックの実装完了"
```

---

##### 5. リファクタリング後（推奨）
コードのリファクタリングを実施した後

**理由**:
- 機能追加とリファクタリングを分離
- レビューしやすくする
- 問題発生時のロールバックを容易にする

**例**:
```bash
# 機能実装
git commit -m "[PBI-002] APIキー保存機能を実装"

# リファクタリング
git commit -m "[PBI-002] APIキー管理コードをリファクタリング

- 重複コード削除
- 関数を分割して可読性向上
- 定数を抽出"
```

---

##### 6. バグ修正時（必須）
バグを修正した後は即座にコミット

**例**:
```bash
git commit -m "[PBI-002] fix: APIキー検証時のエラーハンドリングを修正

- ネットワークエラー時の処理を追加
- タイムアウト設定を10秒に変更

Test: ブラウザで再現確認済み（修正済み）"
```

---

#### コミットしてはいけないタイミング

##### ❌ テストが失敗している時（mainブランチ）
```bash
# NG: E2EテストがFailしている状態でmainにコミット/マージ
npm test  # → FAIL
git commit -m "..."  # ← ダメ！

# OK: featureブランチならWIPとしてコミット可能
git commit -m "[PBI-002] WIP: テスト修正中"
```

---

##### ❌ コンソールエラーがある時（mainブランチ）
```bash
# NG: JavaScriptエラーが出ている状態でコミット
# ブラウザのコンソールにエラー表示
git commit -m "..."  # ← ダメ！

# OK: エラーを修正してからコミット
# エラー修正 → 確認 → コミット
```

---

##### ❌ 既存機能が壊れている時
```bash
# NG: 新機能追加により既存機能が動かなくなった
git commit -m "..."  # ← ダメ！

# OK: 既存機能を修正してからコミット
# または新機能を一時的にロールバック
```

---

#### コミットメッセージのテンプレート

##### 通常の機能実装
```
[PBI-XXX] 簡潔なタイトル（50文字以内）

- 変更内容の詳細（箇条書き）
- 実装したこと
- 考慮したこと

Test: ブラウザで動作確認済み / TC001実施済み（Pass）
```

##### バグ修正
```
[PBI-XXX] fix: バグの簡潔な説明

- 原因: バグの原因
- 対応: 修正内容
- 影響範囲: 影響を受ける機能

Test: 再現手順で確認済み（修正済み）
```

##### リファクタリング
```
[PBI-XXX] refactor: リファクタリング内容

- 変更前: 元のコード構造
- 変更後: 新しいコード構造
- 理由: リファクタリングの目的

Test: 既存テスト全てPass
```

##### WIP（作業途中）
```
[PBI-XXX] WIP: 作業中の内容

- 実装済み: 完了した部分
- 未完了: 残りのタスク

Note: 作業途中、XXを実装予定
```

---

#### コミット粒度のガイドライン

##### ✅ 良いコミット粒度
```bash
# 1つの意図を持つコミット
git commit -m "[PBI-002] APIキー入力フォームのバリデーション追加"

# 関連する変更をまとめる
git commit -m "[PBI-002] APIキーのマスク表示機能を実装

- 設定画面でのマスク表示
- マスク/表示切替ボタン追加"
```

##### ❌ 悪いコミット粒度
```bash
# 複数の無関係な変更を含む
git commit -m "[PBI-002] いろいろ修正"  # ← 何をしたか不明

# あまりに細かすぎる
git commit -m "[PBI-002] 空白を削除"  # ← 細かすぎ
git commit -m "[PBI-002] コメント追加"  # ← 細かすぎ
```

---

#### コミット前のチェックリスト

実行前に確認:

- [ ] **動作確認済み**: ブラウザで動作を確認した
- [ ] **不要なファイルを含まない**: `node_modules/`, `.env`, `*.log` など
- [ ] **コンソールエラーがない**: 重大なエラーが出ていない
- [ ] **console.logを削除**: デバッグ用のログを削除した（必要なものは除く）
- [ ] **コメントアウトコードを削除**: 不要なコメントアウトを削除した
- [ ] **フォーマット済み**: コードが整形されている
- [ ] **コミットメッセージが明確**: 何をしたか分かる

#### 実践例: 1日の作業フロー

```bash
# 朝: 作業開始
git checkout -b feature/PBI-002-api-key-management

# Phase 1完了
git add src/index.html src/styles.css
git commit -m "[PBI-002] APIキー入力モーダルUIを実装"

# Phase 2完了
git add src/app.js src/api-client.js
git commit -m "[PBI-002] APIキー保存・検証機能を実装"

# 昼休憩前（保険のコミット）
git add .
git commit -m "[PBI-002] WIP: エラーハンドリング実装中"

# 午後: Phase 3完了
git add src/app.js
git commit -m "[PBI-002] エラーハンドリングとバリデーション追加"

# リファクタリング
git add src/app.js
git commit -m "[PBI-002] refactor: APIキー管理コードを整理"

# Phase 4完了
git add tests/
git commit -m "[PBI-002] TC001テストケースを実施（Pass）"

# 夕方: PBI完了、mainにマージ
git checkout main
git merge feature/PBI-002-api-key-management
git push

# 煙テスト実施
npm run test:smoke  # → Pass確認
```

#### コミットの取り消し・修正

##### 最後のコミットを修正（まだpushしていない）
```bash
# コミットメッセージを修正
git commit --amend -m "修正したメッセージ"

# ファイルを追加してコミット修正
git add 忘れたファイル.js
git commit --amend --no-edit
```

##### コミットを取り消す
```bash
# 最後のコミットを取り消し（変更は保持）
git reset --soft HEAD~1

# 最後のコミットを完全に取り消し
git reset --hard HEAD~1  # ⚠️ 変更が失われる
```

**注意**: 既にpushしたコミットは`--amend`や`reset`しない（チームに影響）

---

#### Git運用のベストプラクティス

1. **mainは常に動作する状態**
   - mainブランチはプロダクション品質を維持
   - DoDを満たしたもののみマージ

2. **featureブランチでこまめにコミット**
   - 作業の進捗を記録
   - ロールバックポイントを確保

3. **コミットメッセージは未来の自分への手紙**
   - 3ヶ月後に読んでも分かる内容
   - 何をしたか、なぜしたかを記載

4. **1日1回以上はコミット**
   - 最低でも1日の終わりにコミット
   - 作業ロストを防ぐ

5. **pushは慎重に**
   - mainへのpushは必ずテスト後
   - featureブランチはバックアップとしてpush

## 7. コーディング規約

### 7.1 JavaScript規約

#### 命名規則
```javascript
// 変数・関数: camelCase
const apiKey = 'xxx';
function generateSpeech() { ... }

// 定数: UPPER_SNAKE_CASE
const API_ENDPOINT = 'https://...';
const MAX_HISTORY_COUNT = 50;

// クラス: PascalCase
class ApiClient { ... }

// プライベート関数: _で開始
function _validateApiKey(key) { ... }
```

#### コメント
```javascript
// 複雑なロジックには必ずコメントを付ける
// ✅ Good
// 話者名（例: "Joe:"）を検出して発話行を抽出する
const speakerPattern = /^([A-Za-z]+):\s*(.+)$/;

// ❌ Bad（自明なコメントは不要）
// カウントをインクリメントする
count++;
```

#### エラーハンドリング
```javascript
// try-catch で適切にエラーをキャッチする
try {
  const response = await fetch(API_ENDPOINT, ...);
  if (!response.ok) {
    throw new Error(`API Error: ${response.status}`);
  }
  // ...
} catch (error) {
  console.error('音声生成エラー:', error);
  showErrorNotification('音声生成に失敗しました');
}
```

#### セマンティックHTML
```html
<!-- ✅ Good: セマンティックタグを使用 -->
```

## 8. デバッグ・トラブルシューティング

### 8.1 デバッグ手順

#### 問題が発生したら
1. **ブラウザのコンソールを確認**
   - エラーメッセージを読む
   - スタックトレースを確認

2. **console.logでデバッグ**
   ```javascript
   console.log('API Request:', requestBody);
   console.log('API Response:', response);
   console.log('Current State:', appState);
   ```

3. **ブラウザのDevToolsを活用**
   - Network タブでAPI通信を確認
   - Application タブでlocalStorageを確認
   - Elements タブでDOM構造を確認

4. **段階的に原因を特定**
   - 最後に動いていた状態に戻す
   - 1つずつ変更を加えて問題箇所を特定

### 8.2 よくある問題と対処法

#### API呼び出しが失敗する
- [ ] APIキーが正しく設定されているか確認
- [ ] Network タブで実際のリクエストを確認
- [ ] CORSエラーが出ていないか確認
- [ ] リクエストボディのJSON形式が正しいか確認

#### localStorageが保存されない
- [ ] ブラウザのプライベートモードになっていないか確認
- [ ] localStorage容量制限に達していないか確認
- [ ] キー名が正しいか確認

#### 音声が再生されない
- [ ] Blob URLが正しく生成されているか確認
- [ ] audio要素のsrc属性が設定されているか確認
- [ ] Base64デコードが正しく行われているか確認
- [ ] ブラウザのメディア再生許可設定を確認

## 11. スプリント運営

### 11.1 デイリールーチン（推奨）

#### 開発開始時（10分）
1. 今日のタスクを確認
2. 前日の成果を確認（動作する状態か？）
3. ブロッカーがないか確認

#### 開発終了時（15分）
1. **必ず動作する状態にする**（最重要）
2. E2Eテストを実施
3. コミット・プッシュ
4. 明日のタスクを確認
5. 進捗記録

### 11.2 スプリントイベント

#### スプリントプランニング（Sprint開始時、2時間）
1. スプリントゴール確認
2. PBI の詳細確認
3. タスク分解
4. 見積もり確認
5. コミットメント

#### デイリースクラム（毎日、15分）※チームの場合
1. 昨日やったこと
2. 今日やること
3. ブロッカー

#### スプリントレビュー（Sprint終了時、1時間）
1. **デモ実施**（実際にブラウザで操作）
2. スプリントゴール達成確認
3. フィードバック収集
4. 次スプリントへの引き継ぎ

#### スプリントレトロスペクティブ（Sprint終了時、1時間）
1. Keep（良かったこと）
2. Problem（問題）
3. Try（次に試すこと）
4. アクションアイテム決定

## まとめ

このプロセスの核心は**「常に動作する状態を維持し、E2Eテストで確認しながら開発を進める」**ことです。

### 重要な3つの習慣

1. **毎日動かす**: 1日の終わりには必ず動作する状態にする
2. **こまめに確認**: ブラウザで頻繁に動作確認する
3. **壊さない**: 既存機能が壊れていないか常にチェックする

このプロセスに従うことで、高品質で保守性の高いアプリケーションを効率的に開発できます。
