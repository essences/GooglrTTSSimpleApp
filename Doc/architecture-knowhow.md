# アーキテクチャ設計ノウハウ（初めて読む人向け）
研修用ナレーション生成アプリを「小さく始め、必要に応じて段階的に深くする」過程で得た知見をまとめています。プロジェクト詳細を知らなくても読めるよう、背景と選択理由を補足しています。

## 1. スモールスタート → 必要に応じてジャンプ
- 初期は「HTML1枚＋ブラウザ完結」で最小構成。  
- TTS要件が増え、ブラウザだけでは足りなくなった時点で「ローカル簡易サーバー＋フロント分割」に移行。  
- ポイント: 最初から重厚なレイヤーを敷かず、要件の複雑さに応じてアーキテクチャを深くする。
- 用語: アーキテクチャジャンプ＝現行構成が要件を満たせなくなったときに、層やコンポーネント構成を一段階引き上げる判断と実行のこと（例: 単一HTML→簡易サーバー付き→レイヤード/DI→マイクロサービス）。振り返りでリスクが顕在化したタイミングを「ジャンプ」の判断材料にする。

## 2. クラス化とDIが効く理由
- クラス化で責務境界が明確になり、読み込むコンテキストを減らせる。  
- DIコンテナ/レジストリ（例: service-registry）で依存を注入すると、モック差し替えやテストが簡単になる。  
- ファクトリは互換APIを保ちつつ、内部はクラス＋`init/destroy`でイベント管理。`document`やサービス依存を注入して環境を問わず動かせる。
- DIコンテナとは: 依存関係（クラスやサービス）を登録し、生成とライフサイクル管理を自動化する仕組み。呼び出し側は「必要なインターフェース名」で取得するだけで、実装や生成手順を意識しない。テストではモックを挿し替え、本番では実実装を注入するだけで配線変更を最小化できる。
- ファクトリパターンとは: 生成ロジックを隠蔽し、共通インターフェースを返すパターン。DIコンテナと組み合わせると「依存（設定/環境/サービス）をまとめて注入した上で標準化されたインターフェースを返す」ことができ、呼び出し側がコンストラクタや初期化順序を気にせずに済む。

## 3. 規模別のアーキテクチャ例
- 小規模: HTML単体＋ブラウザ完結（依存最小）。  
- 中規模: 簡易バックエンド（ローカルサーバー）＋フロントはクラス/DIで分割。  
- 大規模: レイヤード＋DIコンテナ＋型付け（TSなど）、テスト自動化を前提に設計。
- マイクロサービス: 機能を小さいサービス群に分割し、独立デプロイ＋API/メッセージで連携。利点はチーム分離・スケール粒度・障害封じ込め。代償は分散トレーシングやリリース調整、契約（APIスキーマ）の厳密管理が必要になる点。監視/ロギング/サーキットブレーカーなど運用設計が前提。

## 4. ファイルサイズとコンテキスト
- 2k行超の巨大ファイルは修正コストを押し上げる。クラス分割と責務分離で「読む範囲」を小さく保つ。  
- 関数ベースよりクラスベースの方が参照探索が狭まり、AI/人の理解が容易。

## 5. テスト戦略
- DIでモック注入が容易になり、ユニット＋モックE2Eでリグレッションを抑制。  
- モックTTS/ストレージによりネットワーク非依存のスモークを用意し、CIやローカルで安定確認。

## 6. バックログ運用
- ユーザーストーリーと受入基準で進捗管理。完了PBIは「消化ログ」に記録し、未完リスクは「未完了サマリー」に明示。  
- 大きな要件（例: MP3変換/履歴上限など）は小タスクに分割して優先度を調整。

## 7. 言語選択の比較
| 言語 | 利点 | 留意点（型・スコープ管理など） |
| --- | --- | --- |
| JavaScript | ブラウザ/Nodeで統一運用。クラス構文で構造を明示できる。ビルド不要で小さく始めやすい。 | 静的型なし。モジュールスコープはESM、関数/ブロックスコープのみで強制力弱め（設計/テストで補完）。 |
| TypeScript | 型と構造が得やすく大規模向き。クラス/DIと相性が良い。 | ビルド/ファイル増の管理コスト。モジュールスコープはJS同等だが型で境界を明示しやすい。生成物(JS)とソースの同期管理が必要。 |
| Python | ライブラリ豊富でサーバー実装が楽。クラス/モジュールで責務を分けられる。 | 静的型なし（型ヒント任意）。モジュール/クラス/関数スコープはあるが、可視性制御（private/protected）が弱く設計規律依存。インデント崩れリスクに注意。 |
| Java | 静的型とコンパイラで構造を強制。パッケージ/クラス/メソッドスコープ＋アクセス修飾子(public/protected/private/package-private)で可視性を厳格に制御でき、大規模でも「どこから見えるか」を明確に管理可能。実行速度も高くエンタープライズ向け。 | 設計・設定が重くなりがち。モノリス化しやすいので、大規模ではマイクロサービスを検討（サービス粒度・通信・監視を別途設計）。 |

## 9. 定期振り返りとリスク評価のすすめ
- プロセス振り返り（KPTなど）を定期（例: 週次）で実施し、設計・運用リスクを洗い出してバックログに反映する。必要に応じてアーキテクチャジャンプ（構成見直し）のトリガーにする。
- 現在の主要リスクと軽減策:  
  - MP3変換未実装: 変換方式の決定とZIPまとめDLを小タスク化して着手。  
  - ステータスログ永続化・履歴統合不足: ログの保存先とフォーマットを決めてUI統合する。  
  - トークン/履歴上限・一括DL未対応: 上限値と切り捨てポリシーを定義し、UI警告を追加。  
  - Safety Profileのサーバー側検証不足: サーバーでバリデーションを実装し、クライアントと整合させる。  
  - モノリス化リスク: コントローラー/サービス分割とDIを維持し、粒度が肥大化したら更に分割する。
- リスクは「未完了サマリー」に明示し、「消化ログ」で対策完了を記録することで優先度付けと改善サイクルを回しやすくする。
